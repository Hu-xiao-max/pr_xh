# Add or update a paper in the research deck

## What this repository is

A static, build-free **slide deck** for presenting research: cover with a clickable table of
contents → one slide per paper → one slide per project → closing slide. Entries carry
`section: 'research'` (default) or `'project'`; the contents and closing list are grouped by section
(`SITE.sections`), so keep papers first and projects after them in the array. Everything a visitor sees is generated by
`assets/js/main.js` from **`assets/data/papers.js`**, the single source of truth. The array
order in papers.js is the slide order.

```
<paper folder>/           originals: PDF, raw videos (git-ignored), figure images
assets/videos_web/*.mp4   web copies of the videos (H.264, ≤1280 px, +faststart) + manifest.json
assets/posters/*.jpg      poster frame per video
assets/images/*.jpg       web copies of the images (white-flattened JPEG, ≤1600 px) + manifest.json
assets/data/papers.js     SITE copy + PAPERS entries (metadata, points, gallery, media, layout, bibtex)
tools/optimize_videos.py  folder videos → videos_web + posters   (--dry-run, --force, --posters, --js SLUG)
tools/optimize_images.py  folder images → assets/images          (--force, --js SLUG)
tools/test_page.mjs       headless-Chrome smoke test of the whole deck
tools/snapshot_slides.mjs screenshots + overflow/legibility report per slide
```

Read `references/paper-entry.md` before writing the entry: it holds the annotated template,
the bullet style, the layout cookbook distilled from the seven existing papers, and the fields that
differ for a **project** entry (a robot or system the owner worked on, described from a web page or
the owner's own material rather than a PDF).

## The owner's standing rules — and why

These came from several rounds of feedback; breaking them is the main way to disappoint.

- **It is a PR page for an outside audience, not a profile.** No bio, contact, advisor, author
  lines, conference names, years or submission status anywhere on the slides. Authors and venues
  live only inside `bibtex` (a citation needs them). Keep `venue`, `year`, `status`, `authors` in
  the data for that purpose, but nothing renders them.
- **Slides are for talking over, so text is minimal.** Each paper shows 2–3 short bullets
  (`points`); the paragraph `tldr`, the key numbers (`highlights`) and the abstract only appear
  in the Abstract dialog.
- **Images and videos are the content.** Only the owner's own images from the paper folder go
  on a slide (do not cut figures out of the PDF unless asked). Every image must be drawn
  legibly: at 1280×720 at least 300 px wide or 260 px tall — the test enforces it.
- **Text comes first on every device.** All papers use `layout.mode: 'stack'`: text band on top,
  full-width board of media below; phones then show the text, then one item per row.
- **Each paper gets its own composition** (`layout.board`) chosen from the shapes of its media;
  the most explanatory image gets the biggest cell.
- Content language is English; the owner writes to you in Chinese. Mark every guess with a
  `// TODO` comment in papers.js and list the TODOs in your final message.
- Never commit or push unless asked; finish by giving the publish command. The preview server
  for the real repo normally runs on port 8000 (`lsof -nP -iTCP:8000 -sTCP:LISTEN`).

## Workflow

### 1. Find what is new

`git status --short` (or plain `ls` if the directory is not a git checkout) and compare the
paper folders with the `id`s in papers.js and the keys in the two manifests. New folder → new
paper. New files in an existing folder → update that paper's `gallery` / `media`. Pick a short
kebab-case slug from the paper's theme (e.g. `pour-tactile`) and add `"<folder>": "<slug>"` to
the `SLUGS` map in **both** optimizer scripts so output files get stable names.

If the folder's media clearly belong to another project (a video that shows a different robot
or task than the paper describes), do not invent a story: describe what is actually visible in
the label/caption, mark it `// TODO`, and say so prominently in the report — the owner may have
dropped placeholder files.

### 2. Read the PDF

```bash
pdfinfo <pdf> | grep -E 'Title|Author|Subject|Pages'
pdftotext -f 1 -l 2 <pdf> - | head -120       # title, authors, abstract
```

Take the title verbatim, the abstract verbatim (fix hyphenation), and derive: `shortTitle`
(≤ 6 words), `navTitle` (≤ 2 words), 2–3 `points`, a `tldr`, up to three `highlights`
(number + what it measures), `tags` (keywords), and `bibtex` (use real authors/venue there;
`Anonymous` + "under review" note for double-blind submissions). If the PDF is a slide deck
rather than a paper, write a summary from the slides and set `abstractLabel: 'Summary (compiled
from the slides)'`. Venue/year/status go in the data only.

### 3. Videos

```bash
python3 tools/optimize_videos.py --dry-run   # plan: remux vs re-encode, audio kept or dropped
python3 tools/optimize_videos.py             # converts only what is missing
python3 tools/optimize_videos.py --js <slug> # ready-to-paste `media:` block (w/h/duration filled)
```

Compliant files are remuxed losslessly, others re-encoded (libx264, crf 26, ≤1280 px, +faststart);
digitally silent audio is dropped. Per-video maps in the script: `SPEED` (e.g. `2.0` when the owner
asks for a faster demo; audio is dropped), `CROP` (`"w:h:x:y"` in display pixels, to cut empty
background) and `POSTER_AT`. Phone clips are often stored with non-square pixels (ffprobe
`sample_aspect_ratio` ≠ 1:1, e.g. 480×480 with SAR 240:427 = a 480×854 portrait picture): the script
rescales them to square pixels first, so look at frames **with** `scale=iw:ih/sar` (or `-vf
"scale=iw*sar:ih"`) before choosing a crop, otherwise the picture looks squeezed and the crop is wrong. Decide `kind` per video: a narrated or long overview
(≈ ≥ 60 s) is `main` (`kind: 'overview'`: native controls, never autoplays); short demos are
`clips` (`kind: 'loop'`: muted autoplay while the slide is on screen). Replace the TODO labels
(short, 1–3 words, shown on the video) and captions (one sentence, used as a tooltip). Keep
`audio: true` only if the track is narration; ambient noise just gets an unmute button nobody
wants. You cannot listen, so measure: compare `ffmpeg -i v.mp4 -af volumedetect -f null -` with
the same on a speech band (`-af "highpass=f=300,lowpass=f=3400,volumedetect"`) — narration keeps
most of its energy in the band and `silencedetect` shows pauses; motor hum does not. If the
poster frame is a black or title card, set a better timestamp in `POSTER_AT` and run
`--posters`. To judge a video's content quickly, tile a few frames with ffmpeg (build the
filter string in Python, see Pitfalls) and look at the image with the Read tool. A lone video on a
board is centred at its own aspect ratio (`layout.board: { cols: 1, rows: 1 }`), so a single
portrait clip does not need a dark full-width frame.

The scripts rebuild `manifest.json` from the sources they find and merge in earlier entries whose
outputs still exist, so running them with some raw sources missing (they are git-ignored) is
safe; `--js` works for any slug that has converted files.

### 4. Images

```bash
python3 tools/optimize_images.py             # flattens to white, ≤1600 px, writes manifest
python3 tools/optimize_images.py --js <slug> # ready-to-paste `gallery:` entries
```

Order the gallery by importance (pipeline / teaser first). Look at each image (Read the JPEG)
so your bullets and layout match what it shows. Tiny sources (< 500 px wide) will look soft;
say so in the report.

### 5. Write the entry and compose the slide

Copy the template from `references/paper-entry.md`, paste the `--js` outputs, write the text,
and choose `layout.board` with the cookbook. Insert the entry where it belongs in the PAPERS
array (newest or most important first is the current convention) — the cover contents, digit
shortcuts and closing list update themselves. The cover's contents list fits 7 papers at
1280×720; from 8 it switches itself to tighter rows and from 10 to two columns, so check the
cover screenshot whenever the count crosses one of those marks. Then
`node --check assets/data/papers.js`.

### 6. Verify — never skip

```bash
# serve the repo (reuse a running server; for a copy of the repo pick another port)
python3 -m http.server 8000 &
# headless Chrome with a debugging port (one instance per script run; kill it afterwards)
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --user-data-dir=/tmp/pr-xh-chrome --remote-debugging-port=9223 \
  --autoplay-policy=no-user-gesture-required about:blank &
CDP_PORT=9223 BASE_URL=http://127.0.0.1:8000/ node tools/test_page.mjs
# screenshots + numbers for the new slide at projector, desktop and phone sizes
OUT=/tmp/pr-xh-shots PLAN='[[1280,720,false,["<id>"]],[1920,1080,false,["<id>"]],[390,844,true,["<id>"]]]' \
  MONTAGE=/tmp/pr-xh-shots/montage.png CDP_PORT=9223 BASE_URL=http://127.0.0.1:8000/ node tools/snapshot_slides.mjs
```

Wait a second after launching Chrome before running a script (otherwise `window.PAPERS` may not
exist yet). Then **look at the screenshots with the Read tool** and at the printed numbers:
`overflow` must be 0, `bullets` 3 (or however many you wrote), `images` all ≥ 300 px wide or
260 px tall, nothing clipped, text band above the board. Fix by changing `rows`/`cols`, moving
an item, or shortening a bullet — not by shrinking images. The test must end with `0 failed`.
Its assertions are written to be independent of the number and order of papers (they find the
first paper with loop clips, compute the progress bar from N, and address existing papers by
id); if one still fails only because of an intentional layout change, update that assertion.
Also capture the cover (`"cover"`) when you changed the paper count.

### 7. Report

State what was added (source files → generated files), how the slide is composed, the TODOs the
owner should confirm (venue, uncertain captions, audio), and the publish command:

```bash
cd <repo> && git add -A && git commit -m "Add <paper>" && git push
```

## Pitfalls met before

- zsh parses `$i[...]` as an array subscript: build ffmpeg filter graphs in Python or Node, not
  in inline shell loops.
- Headless Chrome clamps `--window-size` below ~500 px; use device emulation (the scripts do).
- `IntersectionObserver` cannot see through an `overflow:hidden` ancestor; the deck relies on the
  viewport not clipping, so keep that CSS as is.
- `python3 -m http.server` ignores Range requests (seeking long videos locally is slow); GitHub
  Pages serves them fine.
- Raw videos stay out of git (`*/*.mp4` in .gitignore) because GitHub warns above 50 MB; only the
  `assets/` copies are tracked.
